## Context

Мотивация — в `proposal.md`, требования — в `specs/agent-skills/spec.md`.

Существенное для подхода состояние. Справка (`helpText` в `main.go`) уже
перечисляет подкоманды, предусловия и коды возврата, а `doctor` перечисляет
проверки. Полноту справки закрепляет `TestHelpNamesEverySubcommand`: он собирает
строковые метки `switch` в `dispatch()` через `go/parser`. Сессия на каждый
обращающийся к устройству вызов получает от хука `additionalContext` с серийником,
а на отказ — `permissionDecisionReason`. Что и почему сверх этого нужно Claude,
перечислено в спеке.

## Goals / Non-Goals

**Goals:**

- Каждый скилл читается за один заход: короткий `SKILL.md` без `references/`.
  При двух узких сценариях раскладывать каждый ещё на файлы незачем.
- Расхождение скилла с бинарём в самой вредной форме — совет запустить
  несуществующую подкоманду — роняет `make test`.

**Non-Goals:**

- Автоматическая сверка прозы скиллов с README или с поведением.
- Проверка, что Claude Code действительно подгружает скилл по описанию:
  это свойство агента, а не роутера.

## Decisions

**Каталог `skills/` в корне, а не `.claude/skills/`.** В `.claude/skills/` скиллы
подгружались бы в сессии разработки самого роутера, которая пулом не
пользуется. `skills/<name>/SKILL.md` в корне — заодно раскладка плагина Claude
Code: если доставка плагином понадобится, хватит добавить
`.claude-plugin/plugin.json`, ничего не двигая.

**Файл, а не встраивание в бинарь или плагин.** Так решил пользователь: скиллы
подключаются ссылкой в выбранные проекты. Альтернативы были такие. Встраивание
через `go:embed` с подкомандой установки дало бы совпадение версий текста и
поведения ценой новой подкоманды. Плагин дал бы установку одной командой и
доставку хуков, но `doctor` пришлось бы учить видеть хуки плагина.

**Два скилла, а не один с разделами.** Описание каждого точнее попадает в свой
сценарий. Ставить их по отдельности приходится вдвойне, но ставит человек
вручную, один раз на проект.

**Что повторять, а что нет.** Перечень подкоманд, коды возврата и состав проверок
скилл не повторяет и отправляет к `emulator-router help` и `doctor`: они рядом,
в установленном бинаре. Фрагмент подключения хуков и поля файла настроек скилл
подключения приводит сам. В бинаре их нет, а README в подключаемом проекте
недоступен. Ошибку в этих местах ловит `doctor`, которым скилл заканчивается.

**Английский язык**, как у README и у текстов, которые видит Claude Code в
чужом проекте.

**Тест согласованности переиспользует сбор меток `dispatch()`.** Обход AST из
`TestHelpNamesEverySubcommand` выносится в хелпер, который возвращает метки.
Новый тест читает `../../skills/*/SKILL.md`, сверяет `name:` в заголовке с
именем каталога и требует, чтобы каждое `emulator-router <слово>` внутри
кода (инлайн и блоков) было меткой. Ищется только внутри кода, а не во всём
тексте: в прозе «emulator-router is…» — не вызов. Альтернатива — литеральный
список подкоманд в тесте — снова не ловит переименование, ради которого тест и
нужен.

## Risks / Trade-offs

- **Подхватывает ли Claude Code симлинк на каталог в `.claude/skills/`, не
  проверено.** → Первая проверка — после подключения в первый проект: скилл
  виден в `/skills`. Если нет, README предписывает копирование вместо ссылки.
- **Закоммиченная ссылка на абсолютный путь битая у второго участника.** →
  README говорит держать ссылку локальной (`.git/info/exclude`) или копировать.
- **Проза скиллов устаревает вместе с поведением.** → Тест ловит только
  подкоманды и имена. Остальное сверяется на ревью изменения, которое меняет
  поведение. Чем меньше скилл повторяет бинарь, тем меньше ему устаревать.
- **Тест читает файлы вне пакета.** → Путь `../../skills` фиксирован раскладкой
  репозитория. Если каталог переедет, тест упадёт громко: ни одного скилла не
  найдено — это ошибка, а не пройденная проверка.
